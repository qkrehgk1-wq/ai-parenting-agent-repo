# Upgrade Automation Levels

## 목적

기능 업그레이드 팀은 "자동으로 전부 바꾸는 팀"이 아니라, "자동으로 기회를 찾고 정리하되 중요한 반영은 사람 승인 아래 진행하는 팀"으로 설계한다.

이 문서는 업그레이드 자동화의 수준을 3단계로 나눠서, 어떤 작업까지 자동화하고 어디서 사람 판단을 넣을지 기준을 정한다.

## 핵심 원칙

- 최신 기술을 빠르게 따라가되 무분별하게 운영에 넣지 않는다.
- 부모 안전, 브랜드 신뢰, 설명 가능성을 해치는 변경은 자동 반영하지 않는다.
- 자동화는 의사결정을 대체하는 것이 아니라, 더 좋은 의사결정을 돕는 방향으로 사용한다.

## Level 1. 감지 자동화

### 설명

업그레이드 후보를 자동으로 발견하고 정리하는 단계다.
아직 운영 반영은 하지 않고, "무엇을 실험할지"를 뽑아내는 데 집중한다.

### 자동화되는 일

- 운영 병목 수집
- 반복 실패 사례 수집
- 새로운 모델, 프롬프트, MCP 활용 아이디어 기록
- `type:upgrade` 이슈 초안 생성
- 업그레이드 백로그 정리

### 사람이 하는 일

- 어떤 안건을 실제 실험으로 올릴지 선택
- 위험도가 높은 안건 보류
- 우선순위 최종 승인

### 적합한 시점

- 지금 바로 시작 가능
- 초기 운영 체계 구축 단계

## Level 2. 실험 자동화

### 설명

선정된 업그레이드 안건을 작은 단위 실험으로 돌리고, 결과를 비교 정리하는 단계다.
운영 반영 전 검증용 자동화다.

### 자동화되는 일

- 실험 PR 초안 생성
- 업그레이드 전후 차이 비교
- PR 자동 요약
- unresolved 리뷰 스레드 감지
- 실험 결과 리포트 초안 생성

### 사람이 하는 일

- 실험 범위 승인
- 성공 기준과 롤백 조건 승인
- 실험 결과 해석
- 운영 반영 여부 결정

### 적합한 시점

- `type:upgrade` 이슈가 월간 단위로 안정적으로 쌓이기 시작한 뒤
- 대표 에이전트가 병목 데이터를 일정 수준 확보한 뒤

## Level 3. 제한적 반영 자동화

### 설명

위험도가 낮고 반복적인 업그레이드만 자동 반영 후보로 올리는 단계다.
그래도 핵심 운영 흐름은 사람 승인 아래 유지한다.

### 자동화되는 일

- 낮은 위험도의 문서성 개선 PR 자동 생성
- 프롬프트 문구 미세 개선안 제안
- PR 요약 형식 보강
- 리뷰 병목 표시와 다음 액션 제안

### 사람이 반드시 승인해야 하는 일

- 핵심 모델 교체
- 안전 검수 정책 변경
- 부모에게 직접 노출되는 응답 구조 변경
- 의료/발달 관련 민감 표현 기준 변경
- 고위험 자동화 도입

### 적합한 시점

- 업그레이드 팀 운영 기록이 충분히 쌓인 뒤
- 실패 사례와 롤백 규칙이 문서화된 뒤

## 자동화하면 안 되는 영역

아래 항목은 기본적으로 자동 반영 금지 영역으로 둔다.

- 부모에게 직접 전달되는 민감 조언 변경
- 안전 문구 삭제 또는 완화
- 검증 없는 최신 모델 전면 교체
- 수익을 위해 추천 기준을 불투명하게 바꾸는 행위

## 현재 추천 단계

현재 우리 팀은 `Level 1 + Level 2 초입`이 가장 적절하다.

이유:

- 운영 구조는 막 세워졌고
- GitHub MCP 활용 흐름도 이제 시작 단계이며
- 실험은 필요하지만 자동 반영까지 가기엔 검증 기록이 아직 부족하다

즉, 지금은 아래 구조가 가장 현실적이다.

1. 자동으로 업그레이드 후보를 모은다.
2. 자동으로 실험 문서를 만든다.
3. 사람 승인 후 작은 PR로 검증한다.
4. 성공한 것만 운영 반영한다.

## 한 줄 결론

업그레이드는 "완전 자동 교체"가 아니라 "자동 탐지 + 자동 실험 보조 + 사람 승인 반영"이 맞다.
