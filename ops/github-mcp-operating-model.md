# GitHub MCP Operating Model

## 1. 왜 GitHub MCP를 중심으로 두는가

GitHub는 단순 코드 저장소가 아니라 에이전트 간 협업 기록을 남기기에 가장 적합한 장소다.

- 작업 단위가 Issue와 PR로 명확하다.
- 리뷰 기록이 남는다.
- 사람이 마지막 승인권자가 되기 쉽다.
- 어떤 에이전트가 어떤 판단을 했는지 추적 가능하다.

## 2. 에이전트와 GitHub 객체의 매핑

- 질문/아이디어: Issue
- 조사 결과: Issue comment 또는 `research/` 문서
- 초안 작성: Branch + PR
- 수정 요청: Review thread
- 수정 완료 회신: Review reply
- 발행 승인: PR merge 또는 승인 상태
- 배포 기록: Issue comment
- 업그레이드 제안: `type:upgrade` Issue + 실험 PR

## 3. 대표 에이전트의 일일 루틴

1. `_get_repo`로 레포 컨텍스트 확인
2. 진행 중인 핵심 PR 상태 확인
3. `_get_pr_info`로 상태별 분류
4. `_list_pull_request_review_threads`로 막힌 지점 파악
5. 필요한 경우 `_add_comment_to_issue`로 다음 액션 기록

## 4. 검수 에이전트의 루틴

1. `_fetch_pr`로 전체 변경 내용 확인
2. 민감 문장 식별
3. 리뷰 스레드 생성 또는 기존 스레드 확인
4. 작성자가 수정한 뒤 `_reply_to_review_comment`로 확인 결과 남김

## 5. 초기 자동화 목표

첫 단계에서는 완전 자동 머지가 아니라 아래까지 자동화하는 것이 적당하다.

- 주제 발굴
- 이슈 초안 생성
- 조사 노트 작성
- 콘텐츠 초안 작성
- 안전 검수 제안
- 배포문 생성

사람은 마지막 승인만 담당한다.

## 6. 실제 운영에서 중요한 규칙

- 모든 민감 주제는 `risk:medical` 또는 `risk:sensitive` 라벨 부착
- unresolved 리뷰 스레드가 있으면 배포 금지
- 사람 승인 전 외부 게시 금지
- 근거가 빈약한 추천형 콘텐츠는 제휴 링크 삽입 금지
- 업그레이드 이슈는 실험과 도입을 분리해서 관리

## 7. 기능 업그레이드 팀 운영 원칙

기능 업그레이드 팀은 최신 AI 흐름을 무작정 따라가는 조직이 아니라, 우리 운영 구조에 맞는 개선만 선별적으로 도입하는 팀이다.

권장 주기:

- 주간: 운영 병목과 불편 수집
- 월간: `type:upgrade` 이슈 선정과 실험 우선순위 결정
- 분기: 모델, 프롬프트, MCP 구조 재검토

업그레이드 대상 예시:

- 더 적합한 모델 조합
- GitHub MCP 활용 확장
- 안전 검수 루프 고도화
- PR 설명 자동화
- 배포 변환 품질 향상

## 8. 다음 구현 단계

다음 단계에서는 이 저장소를 실제 GitHub 레포로 만들고, 다음을 연결하면 된다.

- GitHub Issue 템플릿
- PR 템플릿
- 라벨 정책
- 자동 요약 에이전트
- 주간 리포트 자동화
